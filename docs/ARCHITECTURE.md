# Архитектура

## Общая схема

```
Telegram ──/start──▶ Бот ──кнопка──▶ Mini App (React SPA)
                      ▲                    │  Authorization: tma <initData>
        уведомления   │                    ▼
              ┌───────┴──────────────────────────────┐
              │  Сервер (Fastify, один процесс)       │
              │  • API клиента      /api/*            │
              │  • API админки      /api/admin/*      │
              │  • webhook бота     /api/telegram/…   │
              │  • статика SPA      / и /admin        │
              │  • фоновые задачи (очередь уведомлений,│
              │    истечение бонусов, напоминания)    │
              └───────────────┬──────────────────────┘
                              ▼
                         PostgreSQL
```

Mini App и админ-панель — одно SPA, один backend и одна база. Это один деплой на одном поддомене (`app.вашдомен`), без CORS и без отдельного `api.`-поддомена.

**Почему не Next.js + NestJS.** ТЗ допускает другой стек при обосновании. Приложению не нужен серверный рендеринг (оно открывается внутри Telegram и закрыто авторизацией), а два фреймворка означали бы два рантайма и заметно больше зависимостей. Fastify + Vite дают ту же типизацию и структуру при одном процессе.

## Структура проекта

```
apps/server/
  drizzle/                 SQL-миграции (генерируются из schema.ts)
  src/
    contract/              общий контракт: статусы, переходы, роли, права, типы API
    db/                    схема Drizzle и подключение
    lib/                   ошибки, деньги (целочисленная арифметика)
    telegram/              проверка подписи, клиент Bot API, обработчик бота
    services/              вся бизнес-логика
      bonuses.ts           жизненный цикл бонуса
      roulette.ts          право на вращение, выбор приза, настройка призов
      orders.ts            заявки, цена, оплата, списание, отмена
      notifications.ts     очередь уведомлений (outbox) и её обработка
      templates.ts         шаблоны сообщений
      admin.ts             выборки для админки, сотрудники, экспорт
      settings.ts          настройки программы
    routes/                HTTP-маршруты (тонкий слой над services)
    cli/                   миграции, сид, создание владельца, настройка бота
  test/                    автотесты
apps/web/src/
  client/                  Mini App: главная, рулетка, бонусы, заказы, профиль
  admin/                   админ-панель
  ui/, styles/             дизайн-система: токены, компоненты, иконки
```

Веб-клиент импортирует `contract/` напрямую из серверного пакета, поэтому статусы, права и типы ответов API не дублируются.

## Авторизация

- **Клиент.** Каждый запрос несёт `Authorization: tma <initData>`. Сервер проверяет HMAC-подпись Telegram и срок давности (`INIT_DATA_MAX_AGE_SECONDS`), затем находит или создаёт профиль по Telegram ID. Идентификатор клиента из тела или параметров запроса не принимается нигде; выборки заказов и бонусов всегда фильтруются по владельцу, чужая запись неотличима от несуществующей (404).
- **Сотрудник.** Тот же `initData` (админка внутри Telegram) либо вход через Telegram Login Widget в обычном браузере — после проверки подписи выдаётся подписанная `httpOnly`, `SameSite=Strict` cookie на 12 часов. В обоих случаях роль и права **на каждый запрос** читаются из таблицы `staff` по Telegram ID, поэтому отзыв доступа действует сразу. Права проверяются внутри каждой сервисной операции, а не только на маршруте.

## База данных

Схема — `apps/server/src/db/schema.ts`, миграции — `apps/server/drizzle/`.

| Таблица                                 | Назначение                                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `users`                                 | Клиенты. `telegram_id` уникален; username — обычное изменяемое поле                             |
| `staff`                                 | Сотрудники: Telegram ID, роль, точечные права (`permissions.grant/revoke`), активность          |
| `orders`                                | Заявки и заказы. `status` и `payment_status` — разные поля. `request_id` — ключ идемпотентности |
| `prizes`                                | Настройка рулетки. Удалённые призы архивируются (`archived_at`)                                 |
| `bonuses`                               | Бонусы со **снимком** условий приза на момент выигрыша                                          |
| `spin_grants`                           | Права на вращение (приветственное, за заказ, выданное вручную)                                  |
| `spins`                                 | Журнал вращений; `(user_id, request_id)` уникален                                               |
| `payments`                              | Подтверждённые оплаты и возвраты                                                                |
| `order_status_history`, `bonus_history` | История каждой смены статуса: кто, когда, почему                                                |
| `audit_logs`                            | Журнал действий сотрудников со снимками «до/после»                                              |
| `user_activity`                         | Лента активности клиента                                                                        |
| `notifications`                         | Очередь исходящих уведомлений                                                                   |
| `settings`                              | Настройки программы (одна JSON-запись)                                                          |

Ключевые ограничения целостности на уровне БД:

- `bonuses_one_open_per_user_uidx` — частичный уникальный индекс по `user_id` для статусов `ACTIVE` и `RESERVED`: второго открытого бонуса у клиента быть не может, даже в обход приложения.
- `bonuses_reserved_order_uidx`, `bonuses_redeemed_order_uidx` — один бонус на заказ.
- `payments_one_confirmed_per_order_uidx` — одна подтверждённая оплата на заказ.
- `spin_grants_order_uidx` — одно вращение за один заказ.
- `spins_user_request_uidx`, `orders_user_request_uidx` — идемпотентность вращений и заявок.
- `CHECK` на допустимые значения статусов и неотрицательные суммы; суммы — `NUMERIC(12,2)`.

### Параллельные запросы

Каждая операция, меняющая бонусы клиента, выполняется в транзакции и первым делом блокирует строку клиента (`SELECT … FOR UPDATE`). Параллельные запросы одного клиента выстраиваются в очередь, второй видит результат первого. Порядок блокировок везде одинаков — заказ → клиент → бонус, — что исключает взаимные блокировки. Уникальные индексы остаются последним рубежом.

## Жизненный цикл бонуса

```
            выигрыш / ручная выдача
                     │
                     ▼
   ┌──────────── ACTIVE ◀─────────────────────────────┐
   │                │  клиент выбрал бонус в заявке    │ отмена неоплаченной заявки /
   │ срок истёк     ▼                                  │ возврат резерва сотрудником
   │            RESERVED ──────────────────────────────┤ (если срок не истёк)
   │                │  оплата подтверждена +           │
   ▼                ▼  сотрудник подтвердил применение │
 EXPIRED ◀──── (срок истёк          REDEEMED ──────────┘
   ▲            за время резерва)        корректировка: только после отмены заказа,
   │                                     с причиной и правом bonuses.correct
 CANCELLED — аннулирован сотрудником (только из ACTIVE, с причиной)
```

- **Заказы через приложение не оформляются.** Приложение — это рулетка и бонусы; заказ клиент обсуждает с менеджером в Telegram. Модуль заказов и оплат на сервере сохранён и покрыт тестами, но в интерфейсе скрыт и не используется.
- У каждого бонуса есть уникальный номер вида `YB-7KQ4MX` (колонка `bonuses.code`). Бонус действует на следующий заказ клиента.
- **«Применить бонус»** (`POST /api/bonuses/:id/apply`): бонус переходит в `RESERVED` — в интерфейсе «Ожидает активации». Повторно применить его нельзя; повторное нажатие лишь снова открывает чат менеджера с готовым сообщением и номером бонуса.
- В момент применения владелец и тимлид (все сотрудники с правом `bonuses.redeem`) получают личное сообщение в боте с кнопками **«Активировать»** и **«Вернуть клиенту»**. Нажавший определяется по Telegram ID из обновления, его права читаются из БД. После нажатия кнопки исчезают, в сообщение дописывается итог.
- **Активация** (`REDEEMED`) — кнопкой в боте или в админке (карточка бонуса, в том числе найденная по номеру). Активировать можно и бонус, который клиент не «применял» кнопкой, а просто назвал номер. Операция идемпотентна: два сотрудника не спишут бонус дважды. После активации клиент получает новое вращение (настройка «Когда клиент получает новое вращение»).
- **Возврат клиенту** — бонус снова `ACTIVE` (или `EXPIRED`, если срок истёк, пока он ждал активации).
- Бонус не списывается при создании заявки и при согласовании цены — только отдельным действием после подтверждённой оплаты.
- Пока бонус в резерве, истечение срока его не трогает. После снятия резерва срок проверяется: `ACTIVE` либо `EXPIRED`.
- Записи не удаляются; каждая смена статуса попадает в `bonus_history`.
- Изменение призов не затрагивает выданные бонусы: условия скопированы в запись бонуса.

| Из                             | Можно перевести в                                           |
| ------------------------------ | ----------------------------------------------------------- |
| Новая заявка                   | Ожидает согласования стоимости · Ожидает оплаты¹ · Отменён² |
| Ожидает согласования стоимости | Ожидает оплаты¹ · Отменён²                                  |
| Ожидает оплаты                 | Ожидает согласования стоимости · Оплачен³ · Отменён²        |

## Правила программы: вращения и бонусы

Цикл: **заказ → вращение (7 дней) → бонус (14 дней) → заказ с бонусом → вращение → …**

| Событие                            | Что происходит                                      |
| ---------------------------------- | --------------------------------------------------- |
| Клиент впервые открыл бота         | Одно приветственное вращение, действует 7 дней      |
| Вращение не использовано за 7 дней | Сгорает (`spin_grants.expires_at`)                  |
| Клиент прокрутил рулетку           | Бонус на следующий заказ, действует 14 дней         |
| Клиент нажал «Применить бонус»     | Бонус ждёт активации; срок 14 дней продолжает идти  |
| Сотрудник активировал бонус        | Бонус использован. Вращение само не начисляется     |
| Бонус не активирован за 14 дней    | Сгорает — и активный, и ожидающий активации         |
| Клиент сделал заказ                | Владелец или тимлид начисляет одно вращение вручную |

Начисление вращения (право `spins.grant`, по умолчанию у владельца и тимлида): на дашборде блок «Начислить вращение за заказ» — поиск по @username или Telegram ID; в карточке клиента; в карточке активированного бонуса; кнопкой «Начислить вращение» в боте под сообщением об активации.

Ограничения, из-за которых бонус нельзя получить, не сделав заказ:

- у клиента не больше одного неиспользованного вращения — второе поверх не начисляется;
- пока у клиента действующий бонус, вращение начислить нельзя;
- сгоревшее вращение или бонус сами нового вращения не дают — только следующий заказ.

Сроки (7 и 14 дней), число приветственных вращений и режим начисления меняются в настройках. Режим «автоматически после активации бонуса» сохранён как настройка.

## Языки

Три языка: русский, английский, украинский (`LOCALES` в `contract/constants.ts`).

- **Выбор.** При первом `/start` бот спрашивает язык кнопками; команда `/lang` позволяет сменить его позже, как и переключатель в профиле мини-приложения (`PUT /api/me/locale`). Пока клиент не выбрал язык, он определяется по языку его Telegram.
- **Бот.** Приветствие, уведомления о бонусах, кнопка меню и подсказки команд — на языке клиента (`services/i18n.ts`). Сообщения сотрудникам и админ-панель — на русском.
- **Мини-приложение.** Все тексты — в словаре `apps/web/src/i18n.ts`. Сообщение менеджеру по кнопке «Применить бонус» тоже составляется на языке клиента.
- **Призы.** Русские название, описание и условия хранятся в основных полях приза, переводы — в `prizes.translations` (редактируются в админке: Рулетка → «Условия»). Перевод копируется в бонус при выигрыше. Без перевода показывается русский текст.
- **Ошибки.** Сервер отвечает по-русски; для других языков приложение подбирает текст по коду ошибки.

## Рассылка

Раздел админки «Рассылка» (право `broadcast.send`, по умолчанию только у владельца).

- **Получатели** — клиенты, которые нажали `/start` (`users.bot_started_at`) и не заблокировали бота (`bot_blocked_at`). Можно разослать всем или только выбравшим конкретный язык.
- **Сообщение** — текст с разметкой Telegram (жирный, курсив, подчёркнутый, зачёркнутый, код, цитата, спойлер, ссылки), переносы строк сохраняются. Одно вложение: фото или голосовое. До восьми кнопок-ссылок и кнопка открытия мини-приложения.
- **Проверка до отправки.** Сервер проверяет разметку (только разрешённые теги, все закрыты, ссылки http/https/tg) и длину (4096 символов, с вложением — 1024). «Отправить себе» показывает сообщение в боте автору.
- **Вложения** загружаются один раз: файл отправляется в личный чат сотрудника с ботом, Telegram возвращает `file_id`, по нему файл рассылается всем.
- **Отправка** идёт в фоне порциями до 25 сообщений в секунду (лимит Telegram). Список получателей фиксируется при создании (`broadcast_recipients`), каждому сообщение уходит один раз; перезапуск сервера рассылку не дублирует и не теряет. Одновременно идёт одна рассылка, её можно остановить.
- Клиент, заблокировавший бота, помечается и в следующие рассылки не попадает; новый `/start` возвращает его в список.

## Уведомления

Уведомление записывается в таблицу `notifications` в той же транзакции, что и бизнес-операция, а отправляется отдельным фоновым процессом. Сбой Telegram не откатывает заказ или бонус. Повторы — с растущей задержкой до 8 попыток; ошибки, которые повтор не исправит (клиент заблокировал бота), сразу помечаются `FAILED`. `dedupe_key` исключает повторную постановку одного события. Командные уведомления идут в рабочий чат, а если он не задан — лично сотрудникам с доступом к заказам.

Гарантия доставки — «хотя бы один раз»: при падении процесса между отправкой и фиксацией сообщение может прийти дважды. На бизнес-данные это не влияет.

## Интеграции и расширение

- **Google Sheets.** Не подключено. Источник данных — собственная база. Точка расширения: таблица `audit_logs` содержит все бизнес-события с идентификаторами сущностей и снимками сумм. Будущий синхронизатор читает её по возрастанию `created_at`, хранит курсор и пишет в таблицу строки с ID записи — это даёт защиту от повторной записи и повторную обработку сбоев по образцу очереди уведомлений.
- **Ограничение частоты запросов** хранится в памяти процесса. При запуске нескольких экземпляров сервера его нужно перевести на общий Redis (поддерживается `@fastify/rate-limit`).
- **Отчётные периоды** считаются в UTC.
